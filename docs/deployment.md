# deployment

react + uppy → hono → sqlite/drizzle + p-queue → mtcute → telegram private channel. caddy terminates https.

the custom service keeps the two-action interface and code-based access small. teledrive's drive dashboard and filesystem model are unnecessary for this flow.

the minimatch 11 override fixes [glob amplification in lint tooling](https://github.com/advisories/GHSA-g3hv-75wg-m249). remove it when those upstream dependencies accept the patched major.

## server

- app: `/srv/tg-drop/app`
- data: `/srv/tg-drop/data` (owned by `tg-drop`, mode 0700)
- secrets: `/etc/tg-drop.env` (root, mode 0600)
- service: `/etc/systemd/system/tg-drop.service`
- caddy: `/etc/caddy/tg-drop.Caddyfile`, imported by `/etc/caddy/Caddyfile`
- backend: `127.0.0.1:8787`

install node.js 24 lts, npm, ffmpeg with ffprobe, and caddy on the server. node must be installed system-wide for systemd to find it. if npm needs to compile native dependencies, install python3, make, and a c++ compiler.

on the server as root, create the service account and directories:

```sh
useradd --system --user-group --no-create-home --shell /usr/sbin/nologin tg-drop
install -d -m 0755 /srv/tg-drop/app
install -d -m 0700 -o tg-drop -g tg-drop /srv/tg-drop/data
```

replace `drop.example.com` in the [caddy config](../deploy/Caddyfile) with your domain. install the `.env` generated by setup as `/etc/tg-drop.env` with mode 0600. set `ORIGIN` to the matching https url, `DATA_DIR=/srv/tg-drop/data`, `HOST=127.0.0.1`, and `PORT=8787`.

run `npm run telegram:login` locally and scan the qr code in your terminal. once the command exits, copy `telegram.session` from your local `DATA_DIR` into the server's data directory with owner `tg-drop:tg-drop` and mode 0600. never run the same session on two machines simultaneously.

to log in directly on the server, run `node --env-file=/path/to/config dist/server/scripts/telegram-login.js` in an interactive ssh session as the service user, with a config file that user can read and the service's `DATA_DIR` set. add `--qr-image` to get a temporary png on the server instead of a terminal qr. copy the png over ssh while the command is running and scan it before the printed expiry. if telegram asks for 2fa, enter the password at the hidden prompt in that same ssh session.

build locally and copy the release to the server. for updates, stop `tg-drop` before syncing.

```sh
npm ci
npm run build
rsync -az --no-owner --no-group package.json package-lock.json dist root@drop.example.com:/srv/tg-drop/app/
scp deploy/tg-drop.service root@drop.example.com:/etc/systemd/system/
```

install production dependencies on the server, then start and verify the service:

```sh
cd /srv/tg-drop/app
npm ci --omit=dev
systemctl daemon-reload
systemctl enable --now tg-drop.service
curl --fail http://127.0.0.1:8787/api/health
journalctl -u tg-drop.service -n 100
```

## behavior

- the sole storage/sync chat is private channel `4304384450` (telegram peer `-1004304384450`), set in `server/telegram-chat.ts`. the telegram account must have access and permission to post/edit/delete. saved messages are never scanned or accessed.
- when switching from saved messages, stop the service and clear the `files` table before starting this version: old message ids belong to a different chat. existing saved-message codes and signed links must stop resolving. keep the session/auth tables.

- dropped folders are packaged into ZIP with zip.js in the browser; archive size is checked before packing and uploading. files stream to temporary disk, then enter a persistent, sequential telegram queue. codes appear after telegram confirms storage.
- staging is limited to 4.5 gb; each file is limited to 4 gb (premium). uploads also check free disk space and keep a 256 mb reserve.
- files and codes remain available until manual removal. downloads can run concurrently; deletion waits for active transfers.
- manual removal revokes access immediately. cleanup retries telegram deletion every 30 seconds if telegram is unavailable.
- documents, video and audio added to the private channel are imported automatically. existing history is scanned in the background. original captions are preserved and the code is appended with inline code formatting.
- telegram stores the original documents in the private channel. manually deleting them there makes those files unavailable.
- browser uploads retry connection/server errors, but do not resume a partial file after a page reload. files already received by the server continue processing.

sqlite and the telegram session are required to recover file access. back up `/srv/tg-drop/data` and `/etc/tg-drop.env` while `tg-drop.service` is stopped, or use sqlite's online backup api. keep backups private. the vps stores metadata and temporary uploads; telegram is the final file store.

## authentication

- the password is verified against a salted scrypt hash on the server. successful password entry creates a random 256-bit session token in an httponly, secure (https), samesite=strict cookie scoped to `/api`.
- sqlite stores only an hmac digest bound to the session secret and password hash. sessions have no server-side expiry and survive restarts. changing either secret invalidates existing sessions.
- the server requests a 400-day cookie lifetime and renews it whenever `/api/session` restores a valid session. browsers may enforce a shorter lifetime. clearing cookies, private browsing cleanup, or browser eviction can still require another login.
- startup checks the session before rendering the entry form, so returning users go straight to uploads without a password-form flash.
- the top-left back button revokes the session in sqlite, clears the cookie and unmounts uploads. failed logout stays on the dashboard and shows an error so it can be retried.
- all `/api/files` routes require a valid session, including listing, upload, owner download, delete and retry. api responses are not cached; writes also require the configured origin.
- public code lookup intentionally grants access to one shared file without owner login. its signed download link lasts ten minutes; the file code remains valid until manual deletion and never grants file-list access.

## credential attempt limits

- `rate-limiter-flexible` uses the existing sqlite connection; no redis or extra service is required.
- anonymous password and code submissions share counters across login and lookup. the third failure per ipv4 address or ipv6 /64 starts a 60-second block. the tenth global failure blocks anonymous credential checks for 60 seconds.
- counting windows last 60 seconds from the first failure; cooldowns start at the threshold failure, including near the end of a window. rejected requests do not extend cooldowns, and successful requests do not clear counters.
- valid owner sessions bypass these limits. the dashboard, session restoration and existing download links stay available during anonymous lockouts. a fresh login is blocked even with the correct password until cooldown ends.
- sqlite preserves limits across restarts; expired rows are removed on attempts. store failures reject anonymous checks with 503. a bounded, single-concurrency queue prevents parallel credential checks from overshooting the budget in this single-process deployment.
- caddy overwrites `x-forwarded-for` with the connecting client's address. keep the backend bound to localhost; if a cdn is added, revisit trusted client-ip handling.
- throttled responses include `retry-after` and a human-readable wait time in the existing entry-form error. no submitted credentials are stored in counters.
